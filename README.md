# beijing-xiaoqu-ditu · 北京小区地图

把北京市 **10,330 个住宅小区**的物业费、业委会 / 物管会成立情况画成一张可以下钻的地图：全市 → 区 → 街道，一直看到每个小区的明细。

物业费多少钱一平米、有没有业委会、谁在管——这些信息在北京市住建委网站上逐个查都有，但没人愿意查一万次。这个项目把它全量抓下来、拆成结构化数据，再做成可以按区、按街道对比的交互地图。

除了地图，还有一张 **街道列表**：298 个街道 / 地区排成表格，可以排序、筛选、展开看该街道的小区名单；也能切到**小区明细**，把某个区的小区全部铺开成一张表。都支持一键复制成 Markdown 表格或导出 CSV，适合拿去线下核对。两张视图互相跳转，筛选条件也能通过链接分享。

> **在线预览** <https://beijing-xiaoqu-ditu.yaozeyuan.online/>

## 项目约定

这三条是全项目的默认规则，改数据、加导出、写结论前都按它来。

| # | 约定 | 具体落地 |
| --- | --- | --- |
| 1 | **公开项目，人名与手机号一律打码** | 姓名只留首字、其余 `*`；电话只留前 3 位、其余 `*`；单字姓名直接记 `*`；字段名含「姓名 / 联系方式 / 电话 / 手机」的列自动纳入，企业法定代表人同样处理，规则固化在 `crawler/anonymize.py`。含未脱敏内容的 `raw_data/`、`exports/` 只留本地，不入库、不上传 |
| 2 | **默认以政府备案数据为准** | 项目目的是为计算北京小区自治情况提供依据。业委会 / 物管会状态、物业费、收费方式、公共收益等结论性字段一律取备案值；链家库与互联网补查只作补充（户数、建成年代、经纬度、参考价），并标注来源 |
| 3 | **对外数据默认 CSV + JSON 各一份** | 商业小区数据库价格高，公开这套数据也是为了让别人不必重复购买或抓取。`public_data/` 下每个文件同时给 `.csv`（UTF-8 BOM，Excel 直接打开）与 `.json`（`{meta, count, data}`）；新增数据集必须同步更新 `manifest.json` 与「数据下载」页 |

**第 2 条的口径**：默认分母是备案项目（10,495 条），不是链家去重后的 5,655 个小区，也不是地图上的 10,330 个。用到小区级视图时必须写明去重规则（发布版台账按「链家 id，否则区 + 备案名」得到 8,949 个）。算治理比例前先过滤 `备案登记完整 = 是`，否则残缺记录会把成立率压低一半。

**第 3 条的例外**：`web/public/data/发布版/` 的中文台账面向人工阅读，目前只给 CSV 加字段说明、数据说明；程序化处理请用 `public_data/` 的双份文件。

## 两个视图 / 两个层级

同一份数据有三种看法，互相可跳转：

| 视图 | 粒度 | 适合看什么 |
| --- | --- | --- |
| **地图视图** | 区 → 街道 | 空间分布：哪个区密度高、哪个街道自治率低。点区下钻到街道，点街道看该街道小区 |
| **街道汇总**（列表） | 一行一个街道 | 具体数字：298 个街道排序、筛选，点行展开该街道小区名单（名单表头也能排序） |
| **小区明细**（列表） | 一行一个小区 | 区 / 街道下的完整清单，按物业费、建成年代、治理状态排 |

列表页顶部有「街道汇总 / 小区明细」切换，选中区或街道后再切到明细，就是**这个区、这个街道下的小区全表**。

### 单小区详情与政府原页面

三张表（地图页底部名录、街道展开名单、小区明细）的每一行都留了两个入口：

- **点小区名** → 弹出详情：治理状态、计费方式、建成年代、业委会人数、物业企业，以及**物业费逐档构成**（业态 / 房屋性质 / 建筑类型 / 单价）。
- **点行末的 ↗** → 直接打开北京市住建委的该项目原页面，看地址、公共收益、企业评价等级等本站没有收录的字段。链接由项目编号拼成，10,271 / 10,330 个小区可直达；其余 59 个没有项目编号的，图标置灰并给出说明。

### 一键复制

列表页有三处复制按钮，复制出来的都是 Markdown 表格，粘到微信、飞书、Word 里仍然对齐可读：

| 位置 | 复制内容 |
| --- | --- |
| 页面顶部「复制分享链接」 | 当前整屏状态的链接 |
| 「复制汇总表」 | 当前筛选下的全部街道汇总（含合计行） |
| 展开某个街道后的「复制本街道」 | 该街道的小区名单 |
| 小区明细表的「复制表格」 | 当前筛选下的**全部**小区（不受分页限制） |

需要落到 Excel 时用旁边的「导出 CSV」（带 BOM，Excel 直接打开不乱码）。

### 链接可以直接指向某个区、某个街道

任何筛选、排序、下钻、层级切换都会实时写进地址栏，复制出去对方打开就是同一屏。

视图由**路径**决定，其余条件放在 query 里：

- `/` 地图视图
- `/list` 街道列表 / 小区明细

这样两个页面在访问统计里是分开的。切换视图会记一条历史，后退键能回到上一个视图；调筛选只替换当前地址，不会把历史塞满。

| 参数 | 含义 | 取值 | 示例 |
| --- | --- | --- | --- |
| `level` | 列表层级 | `street`（默认）/ `project` | `project` |
| `district` | 城区 | 全名或简称，多选逗号分隔 | `东城区`、`东城`、`东城区,西城区` |
| `street` | 街道 | 可省略「街道 / 地区 / 镇」后缀 | `东华门街道`、`东华门` |
| `metric` | 地图着色指标 | `count` / `rate` / `feeAvg` | `rate` |
| `regime` | 治理状态 | 业委会 / 物管会 / 未成立 / 未知，多选逗号分隔 | `未成立` |
| `fee` | 物业费区间（元/㎡·月） | `最小值-最大值`，可只写一边 | `1-3`、`2-`、`-2.5` |
| `kw` | 关键词 | 匹配小区名 / 街道 / 物业公司 | `东华门` |
| `band` | 自治率区间 | `low`（<30%）/ `mid`（30–60%）/ `high`（≥60%） | `low` |
| `sort` | 列表排序 | `字段:asc\|desc` | `rate:asc` |
| `psort` | 展开街道后小区表的排序 | `字段:asc\|desc` | `fee:desc` |
| `size` | 每页条数 | `10`（默认）/ `20` / `50` / `100` / `1000` | `50` |
| `page` | 页码 | 从 `1` 开始，默认 `1` | `2` |

`sort` 可用字段：`district` `street` `count` `ywh` `wgh` `none` `unknown` `rate` `feeAvg` `feeCount`。
`psort` 可用字段：`name` `regime` `fee` `year` `feeMode` `company`（默认 `regime:asc`，即「未成立 → 物管会 → 未知 → 业委会」）。

旧格式 `?view=list` 仍然可用，会被自动重定向到 `/list` 并保留其余参数。

以**东城区**为例：

```
# 地图看东城区（下钻到街道）
https://beijing-xiaoqu-ditu.yaozeyuan.online/?district=东城区

# 街道列表：东城区各街道，按自治率从低到高，便于找治理洼地
https://beijing-xiaoqu-ditu.yaozeyuan.online/list?district=东城区&sort=rate:asc

# 街道列表 + 定位到东华门街道，自动展开该街道小区名单
https://beijing-xiaoqu-ditu.yaozeyuan.online/list?district=东城区&street=东华门街道

# 同上，展开的名单再按物业费从高到低（只影响展开表，不影响上面的街道行）
https://beijing-xiaoqu-ditu.yaozeyuan.online/list?district=东城区&street=东华门街道&psort=fee:desc

# 小区明细：东城区全部小区铺开成一张表
https://beijing-xiaoqu-ditu.yaozeyuan.online/list?district=东城区&level=project

# 地图看东城区，只看还没成立业委会 / 物管会、物业费 1–3 元的小区
https://beijing-xiaoqu-ditu.yaozeyuan.online/?district=东城区&regime=未成立&fee=1-3

# 小区明细：东城区未成立自治组织的小区，按物业费从高到低
https://beijing-xiaoqu-ditu.yaozeyuan.online/list?district=东城区&level=project&regime=未成立&sort=feeAvg:desc
```

中文在浏览器地址栏里显示为中文，实际传输是百分号编码，两种写法等价，手改也认。简称会自动补全：`district=东城` 等同 `district=东城区`，`street=东华门` 等同 `street=东华门街道`。

两个视图里 `district` 的含义略有差别，这是有意的：地图视图的 `district` 表示**下钻到哪个区**（顶部 KPI 仍是全市口径），列表视图的 `district` 表示**筛选哪个区**（汇总结算只算该区）。切换视图时当前选区会自动带过去。

## 数据文件

正式数据集：**`crawler/data/projects.json`**，10,496 条，一行一条的 JSON 数组。

原始抓取结果在 `raw_data/raw_projects.jsonl`，含未脱敏的联系方式，**不进仓库**；正式数据集由 `crawler/build_dataset.py` 从它生成。

比原始数据多做了三件事：

**1. 人名与电话脱敏**

凡是人名一律打码：姓名只保留第一个字，其余替换为 `*`（`张三丰` → `张**`），单字姓名直接记 `*`；联系电话只保留前 3 位（`13600123000` → `136********`）。

覆盖 `项目负责人姓名`、`业委会(物管会)负责人姓名`、`法定代表人` 与两个联系方式字段，并按字段名兜底——以后政府页面新增的列，只要名字里带「姓名 / 联系方式 / 电话 / 手机」就会自动打码，不需要改代码。规则见 `crawler/anonymize.py`，`build_dataset.py` 生成正式数据集时直接调用。含未脱敏内容的原始文件只在 `raw_data/` 本地存放，已由 `.gitignore` 与 `.vercelignore` 排除。

**2. 「物业服务费用标准」拆成结构化明细**

原始字段是一条把好几层信息压在:`:`里的字符串，一个小区还可能有多个业态：

```
居住类-普通商品房-高层住宅:2.5(元/月.平方米); 非居住类-写字楼:25.32(元/月.平方米)
```

拆成 `物业费明细` 数组，每档一个对象：

```json
"物业费明细": [
  {"业态": "居住类", "房屋性质": "普通商品房", "建筑类型": "高层住宅", "单价": 2.5, "单位": "元/月.平方米"},
  {"业态": "非居住类", "房屋性质": "-", "建筑类型": "写字楼", "单价": 25.32, "单位": "元/月.平方米"}
]
```

- `业态`：居住类 / 非居住类 / 商住类 / 综合类 / 写字楼 / 行政办公 / 商业类
- `房屋性质`：普通商品房 / 房改房 / 回迁房 / 央产房 / 保障房 / 别墅 / 自管公房 / 直管公房 等
- `建筑类型`：高层住宅 / 多层住宅有电梯 / 多层住宅无电梯 / 其它住宅 / 非高层住宅 等
- 原始字符串仍保留在 `物业服务费用标准` 里，方便核对

有些小区只登记两段（如 `居住类-高层住宅:2.5`，第二段其实是建筑类型），所以拆解按词表判断各段属于哪一层，不是按位置硬切。10,496 条里 8,766 条拆出了明细，共 12,753 档价格；1,730 条没有费用标准。

**3. 补上所属街道**

住建委数据只有「区 + 项目地址」，没有街道。街道从小区清单补齐，按可靠性依次尝试：

| `街道来源`  | 判定方式                                               | 条数  |
| ----------- | ------------------------------------------------------ | ----- |
| `address`   | 项目地址里直接写了街道名                               | 1,739 |
| `name`      | 同区内有同名小区                                       | 7,022 |
| `name_dup`  | 同区同名小区分属多个街道，取其中一个                   | 3     |
| `name_only` | 该小区名全市唯一，用它所在的区与街道（顺带回填空白区） | 1,479 |
| `none`      | 匹配不到，`所属街道` 填 `-`                            | 253   |

其中 1,479 条记录详情页只回了项目名称和业委会状态、区与地址都是空，是靠 `name_only` 连区一起补回来的。补完后仍有 237 条无区、253 条无街道。

## 公开数据集（`public_data/`）

上面的 `projects.json` 只有政府侧字段，没有户数和经纬度。`public_data/` 是**把政府备案数据和链家小区库对齐之后**的公开数据集，已脱敏，每个文件同时给 CSV 与 JSON 两份：

```
public_data/
  README.md              总说明（含四个口径坑）
  dictionary.csv         全部字段的含义与实测填充率
  manifest.json          文件清单，网页的数据下载页读这个
  raw/                   原始数据，未经加工
    gov_projects        10,495  政府备案的全量小区项目
    lianjia_2018         9,878  链家开源小区库（2018.11）
    lianjia_2019        10,101  链家开源小区库（2019.02）
  processed/             加工结果
    xiaoqu               5,655  小区级主表，按链家小区去重
    matched              7,194  备案项目 ↔ 链家小区匹配明细
    unmatched            3,301  未匹配的备案项目 + Top3 候选
    beian_master        10,495  备案项目主表（一行一条备案，47 列，含 AI 补查的户数与置信度）
```

`raw` 是「我们手上有什么」，`processed` 是「接起来之后得到了什么」。分开是为了让别人能拿 raw 自己重跑匹配、复核我们的结果，而不是只能相信 processed。

对齐的难点是两边名字经常对不上：备案记「今家园」、链家叫「宣海家园」；备案按楼栋拆成多条、链家合成一条展示。程序规则做完是 49.8%，剩下的交给大模型逐条语义判定，最终 **7,194 / 10,495 = 68.5%** 的备案项目找到了对应小区，去重后 5,655 个小区有户数。

网页上的「数据下载」页（`/data`）列了这七个文件的下载入口和用法示例，另附三份中文台账（明细 / 小区去重汇总 / 字段说明），只给 CSV、Excel 双击能读。

几个容易踩的坑：

- **统计要用 `processed/xiaoqu`**。`matched` 里一个小区可能占多行（备案按楼栋登记），直接统计会重复计数。
- **先过滤 `备案登记完整 = 是`**（最容易踩）。备案库里有 2,036 条只填了项目名、区、街道和收费方式的记录，地址/物业公司/物业费明细全空、业委会状态清一色「均未成立」，且 75% 的酬金制记录都是这种残缺状态（包干制只有 3%）。不过滤会得出「酬金制小区几乎不成立业委会」的假结论——只看完整记录，酬金制 26.3% 反而略高于包干制 24.7%。
- **`房屋性质`**（普通商品房/房改房/央产房/回迁房/保障房/别墅/公房）是这套数据里唯一的产权性质来源，藏在备案的物业费明细里，做治理分析时比建成年代更能解释差异。
- **户数分 `户数` 与 `AI户数` 两列**，前者是链家一对一匹配值，后者是互联网补查值；先看 `AI户数口径`（单条备案 / 本备案分区 / 整小区合计 / 整小区合计·分区未拆）再用。带「分区未拆」的 755 条是多条备案共用一个小区总数，求和前必须按 `链家id` 去重。
- **`AI户数置信度`** 记 A 政府官方 / B 官媒或政府背景媒体 / C 百科或权威行业 / D 房产平台多源互证；空表示该值来自早期轮次，没做分级。
- **`链家为聚合页 = 是`** 表示链家把多个院落合成一条，户数是合计值。
- **`是否住宅 = 否`** 的是写字楼/商场，做住宅分析要剔除。

### 户数是怎么补齐的

备案库本身没有户数。10,495 条备案里**只有 4,792 条能在链家开源库一对一匹配到户数**，其余靠互联网公开页面逐条检索补。检索不靠猜：每个候选值都要用备案的区 / 街道 / 地址做实体核对，核对不过的不进采纳列。

结果：链家 4,792 条 + 互联网补查 3,324 条 = **8,115 条备案有户数（77.3%）**，对应前端地图上 7,954 个小区。补查分四轮，最后一轮专门处理剩余 3,496 条无户数备案，逐条登记（`raw_data/ai_lookup_m3/`，不随仓库发布），361 条采纳、767 条有候选但无法判定、2,368 条查无。

第四轮起对每个采纳值分级，361 条的分布是 A 政府官方 89 / B 官媒 62 / C 百科 98 / D 平台互证 112。另有七类数字一律不采信（E 级）：分批配租套数、批准销售套数、社区辖区户数、整盘合计、单栋单期数、近名不同项目、常住人口数——这类数在原文里和「户数」长得一样，但口径不是本备案。

数值规则只有三条：有值写原值、实际登记 0 写 `0`、无值写 `-`；不拿 0 或估算值填充缺值。

重新生成：

```bash
cd crawler
python build_db.py         # 需要 raw_data/lianjia/ 下的链家库与匹配结果
python export_dataset.py   # 输出 public_data/{raw,processed}/ 和网页用的 dataset.json
cd ../web && npm run build # 数据清单会随前端一起打包
```

## 口径（引用数字前请看这里）

不写清楚口径的统计数字基本没法用，所以这一节比上面那张表重要。

**物业费**
- 一个小区常同时登记多个业态（高层住宅、多层住宅、商业、办公）。统计时**只取居住类**，非居住类在明细里单独标出。
- 同一小区还会按**房屋性质**分档登记：普通商品房、房改房、回迁房、央产房、保障房、别墅……同一个院子里回迁房 1.0、商品房 2.58 是常态，不是异常。只报一个数会让人以为回迁房也按 2.58 收。
  - 列表里物业费**显示区间**（如 `1.00 – 2.58`）并标注有效档数；只有一档有效价格时直接显示该单价。点小区名可看逐档构成。
  - **多档但单价相同**（如橡林郡三档都是 4.98）不是分档收费，显示单价加 `3档` 角标，不当作区间。
  - 没有有效住宅单价时按原因分开显示，不一律写成「非住宅」：登记价全是 0 → `未填`；只有超过 20 元的 → 单价标红加 `超限`；只有综合类 → `综合类`；确实只有非居住类 → `非住宅`。此前这四种情况统一显示「非住宅」，共涉及 **1,683** 个小区，其中 **1,413** 个是误判（476 个多档同价、881 个登记 0 元、32 个超上限、24 个综合类），修正后真正属于非居住类的只有 **270** 个。
  - 排序、地图着色和「平均物业费」KPI 仍需要一个单值，用的是**主力建筑类型组内的中位数**（优先高层住宅，其次多层无电梯，再其次其他居住类）。这个值和区间可能不一致——富贵园主值 1.00（高层组里两档回迁房）、区间 1.00–2.58，正是需要把构成摊开来的原因。
  - 全量 **2,210** 个小区按档登记，其中 **1,734** 个各档单价不同、列表上显示区间；**3,649** 个带构成明细。
  - 区间只统计居住类的有效单价：**0 元多为未填报占位、超过 20 元的多为录入笔误**，两者不进区间，但在明细表里保留原值并标注「疑未填 / 偏高」。
- **22 个小区登记的住宅物业费 > 20 元/㎡·月**，属填报错误（最高一条登记 12,970 元）。明细里原值保留，前端标红且不计入均值与分位数。全部数据里这类异常档位共 66 档。
- **2,124 个小区是酬金制**，按成本据实结算，本来就没有固定单价。所以"有物业费 7,448 个"不等于"剩下 2,882 个没交物业费"。
- 1,730 条记录没有任何费用标准，多为残缺记录，不参与费用统计。

**业委会状态**
- 原始字段是"是否成立业委会(物管会)"，归一化为 业委会 / 物管会 / 未成立 / 未知 四类。
- 59 个小区该字段为空，记为未知，不计入任何比例。
- "自治率"= (业委会 + 物管会) / 有该字段记录的小区数。物管会由街道组建，与业主自己选出的业委会不是一回事，前端把两者分开显示。

**空间精度**
- 住建委数据里**没有小区经纬度**，只有"区 + 项目地址"。所以地图按行政区聚合：全市显示区、点击下钻到街道，**不存在单小区点位**。
- 街道边界覆盖 **93.2% 的小区**（269 / 293 个「区 + 街道」组合）。剩下 24 个街道画不出块，都是 2018 年后新设的建制（丰台六里桥 / 看丹 / 成寿寺、通州九棵树 / 临河里、昌平龙泽园 / 回龙观等），公开的街道边界数据集只更新到那之前。这些街道的小区在右侧明细表和底部名录里仍然完整，只是地图上没有对应的多边形，页面会提示缺了几个。
- 名称对齐：先精确匹配；失败后去掉「街道 / 地区 / 镇 / 乡」后缀按核心词匹配，**且只有候选唯一时才采用**。北京的「X 地区」与「X 镇」是同一实体（地区办事处与镇合署），共 48 个走这条规则；「海淀镇」和「海淀街道」是两个不同街道，靠"精确优先"避免误配。
- 街道边界只作示意，不作测绘或行政依据。

## 复现

### 前端

```bash
cd web
npm install
npm run dev        # http://127.0.0.1:5173
npm run build      # 产物在 web/dist
```

前端数据 `web/public/data/projects.json` 已在仓库里，所以**部署不需要跑 Python**，只装 Node 依赖即可。

### 部署到 Vercel

仓库根已放好 `vercel.json`，前端在 `web/` 子目录这件事已经写死在里面：

```json
"installCommand": "cd web && npm ci",
"buildCommand":   "cd web && npm run build",
"outputDirectory": "web/dist"
```

在 Vercel 上 Import 这个仓库后**不要动 Root Directory**（保持默认的仓库根），直接 Deploy 即可，Framework Preset 会自动识别为 Vite。若手动填了 `web`，反而会去找 `web/web/package.json` 而失败。

命令行部署：

```bash
npm i -g vercel
cd /d/win_www/beijing-xiaoqu-map
vercel --prod
```

`raw_data/` 已在 `.vercelignore` 里排除，不会被上传。

### 说明

推送到 `main` 后由 Vercel 自动构建部署（GitHub Actions 的 Pages 流程已移除，见 `vercel.json`）。

`/list` 这类前端路由需要 SPA 回退，`vercel.json` 的 `rewrites` 把非静态请求都交给 `index.html`（`assets/`、`data/`、`_vercel/` 除外）。本地用 `vite preview` 或 `npm run dev` 时框架自带回退。

访问统计用 Vercel Web Analytics（`@vercel/analytics`，不写 Cookie、不做跨站追踪），只在生产构建里注入 `<Analytics />`，本地 `npm run dev` 不发请求。需在 Vercel 项目的 Analytics 面板里开启后才有数据。

`@vercel/analytics/vue` 的入口会 `import { useRoute } from 'vue-router'`（可选 peer 依赖），所以 `package.json` 里装了 `vue-router`；路由本身也是用它的 `createWebHistory` 跑的，见 `src/router.js`——`/` 和 `/list` 两个路径只用来表达视图，页面上不渲染 `<RouterView>`（两个视图共用同一个 App 和数据）。

统计是按**页面路径**聚合的：`/` 和 `/list` 分开计数。筛选、下钻只改 query，不会算成新的浏览——`beforeSend` 里把「路径没变」的重复 pageview 丢掉了，否则在里面调十次筛选就会多出十条访问记录。

### 从抓取到上线

```bash
cd crawler
pip install -r requirements.txt
python crawl_all.py            # 列表 + 详情，可随时 Ctrl+C，重跑自动续传
python build_dataset.py        # 脱敏 + 拆物业费 + 补街道 → data/projects.json
python sync_site.py            # 生成前端数据 + npm run build
```

`build_dataset.py` 需要两个输入，都在 `raw_data/`：

- `raw_projects.jsonl` — `crawl_all.py` 抓下来的详情
- `xiaoqu_list.md` — 区 / 街道 / 小区名的 Markdown 表格（`| 城区 | 街道 | 小区名 |`）

两个阶段各自落盘缓存，中断不丢进度：

- 列表 → `crawler/data/list_cache.jsonl`（按页缓存，逐行容错，半行损坏不影响整批）
- 详情 → `raw_data/raw_projects.jsonl`（按 `project_no` 去重，失败记录允许重抓）

### 街道边界

```bash
python tools/build_streets.py                 # 下载 16 个区，转换坐标系，简化，拆分
python tools/build_streets.py --refresh       # 强制重新下载（默认读 raw_data/streets_raw/ 缓存）
python tools/build_streets.py --tolerance 0.0002   # 简化容差，单位是度
```

输出 `web/public/data/streets/{区名}.json`，共 16 个文件 1.6MB。前端只在下钻某个区时才请求对应的那一份（东城 25KB、朝阳 82KB、密云 176KB），首屏不受影响。

### 只查几个小区

```bash
python bjjs.py search 万柳书院            # 按小区名
python bjjs.py company 万科               # 按物业企业
python bjjs.py batch names.txt            # 批量，每行一个小区名
python bjjs.py export                     # 已抓数据导出 Excel / CSV
```

## 抓取纪律

政务服务器不是拿来做压测的。项目里的默认参数就是按"别把站点打挂"设的：

- 每个请求**成功后**休眠 1 秒（失败则指数退避，不抢跑）
- 详情 5 并发，列表 5 并发 —— 实测 8 并发时对方响应时间会涨到 20 秒，所以降到 5
- 全程断点续传，重跑只补缺失部分，不做无意义的重复请求
- 只抓公开页面，不绕鉴权、不碰需要登录的接口

如果二次开发，请把 `DELAY` 保持在 1 秒以上。

## 已知局限

1. **数据是某一时点的快照**，业委会成立、物业更换都在持续发生，住建委页面更新后需要重跑。
2. **跨源匹配靠小区名**。清单和住建委的名称不完全一致（"XX家园" vs "XX家园(东区)"），街道有 253 条匹配不到（填 `-`），其中 237 条是详情页缺区缺地址的残缺记录。
3. **一个小区可能对应多条物业项目记录**（分期开发、多物业公司），当前按 `project_no` 去重、按名字择优，未做人工校核。
4. **费用字段有录入错误**，除 22 个超过 20 元的小区外，还有把年费或总额填进单价的极端值（最高 12,970 元）。原值保留，用之前建议按 20 元上限过滤。
5. 建成年代缺失约 1,600 条，不影响费用与自治分析，但按房龄分组时样本会偏。

发现错配或更好的匹配规则，欢迎提 issue。
